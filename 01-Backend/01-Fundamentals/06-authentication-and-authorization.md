# Authentication & Authorization

## 1. Authentication vs Authorization

- **Authentication** → Verifies who the user is.
- **Authorization** → Determines what the user is allowed to do.

---

# Authentication

## 2. Password Authentication

Never store plain-text passwords.

Use password-specific hashing algorithms:

- Argon2id
- bcrypt
- scrypt
- PBKDF2

Avoid using fast hashes directly for passwords:

- MD5
- SHA-1
- SHA-256

---

## 3. Salt

A salt is a unique random value used with a password before hashing.

    Password + Random Salt
              ↓
           Hashing
              ↓
         Password Hash

### Why Salt?

- Makes identical passwords produce different hashes.
- Protects against rainbow-table/precomputed attacks.
- Salt is not secret and can be stored with the hash.

With bcrypt and Argon2, the salt is generally generated automatically as part of the password-hashing process.

---

## 4. Pepper

A pepper is a secret value added to the password before hashing.

    Password + Salt + Pepper
              ↓
             Hash

### Salt vs Pepper

| Salt | Pepper |
|---|---|
| Unique per password | Secret value |
| Not secret | Must remain secret |
| Stored with password hash | Stored outside the database |
| Usually generated by hashing library | Managed by application/secrets infrastructure |

Pepper can be stored in:

- Environment variables
- AWS Secrets Manager
- Azure Key Vault
- HashiCorp Vault

---

# Password Hashing

## 5. bcrypt

Example:

    const hash = await bcrypt.hash(password, 12);

`12` is the cost factor.

    Higher Cost
         ↓
    More Computation
         ↓
    Slower Hashing
         ↓
    Harder Brute-Force Attacks

bcrypt automatically generates a random salt.

### Verify Password

    const isValid = await bcrypt.compare(password, hash);

# Session-Based Authentication

## 6. Session Authentication

In session-based authentication, the server stores the authentication state.

    Login
      ↓
    Server validates credentials
      ↓
    Server creates session
      ↓
    Session ID stored in HTTP-only cookie
      ↓
    Browser sends cookie with requests
      ↓
    Server looks up session
      ↓
    User authenticated

Example:

    Set-Cookie: sessionId=abc123; HttpOnly; Secure

### Key Point

**Session → Authentication state is stored server-side.**

Session data can be stored in:

- Database
- Redis
- Other session stores

---

# JWT Authentication

## 7. JWT

JWT is a token format commonly used for token-based authentication and authorization.

After login:

    User
     ↓
    Login
     ↓
    Server validates credentials
     ↓
    Access Token + Refresh Token

The client sends:

    Authorization: Bearer <access_token>

### JWT Structure

    Header.Payload.Signature

Example:

    xxxxx.yyyyy.zzzzz

### Important

JWT is **signed, not encrypted by default**.

Do not store sensitive information in the JWT payload.

---

## 8. Access Token

An access token is used to access protected APIs.

Example:

    GET /api/profile
    Authorization: Bearer <access_token>

Usually:

- Short-lived
- Used frequently
- Sent with API requests

---

## 9. Refresh Token

A refresh token is used to obtain a new access token after the access token expires.

    Access Token
         ↓
       Expires
         ↓
    Refresh Token
         ↓
    New Access Token

Refresh tokens are generally:

- Long-lived
- More sensitive
- Stored more securely
- Used only with the token endpoint

---

## 10. Access Token vs Refresh Token

| Access Token | Refresh Token |
|---|---|
| Short-lived | Long-lived |
| Used for API requests | Used to obtain a new access token |
| Sent frequently | Sent rarely |
| More exposure | Should be protected carefully |
| Usually has limited lifetime | Usually has longer lifetime |

---

# OAuth 2.0

## 11. OAuth 2.0

OAuth 2.0 is primarily an **authorization framework**.

It allows an application to access resources on behalf of a user without knowing the user's password.

Example:

    Your App
       ↓
    Authorization Server
       ↓
    User gives permission
       ↓
    Access Token
       ↓
    Your App
       ↓
    Resource Server / API

Example:

Allow an application to access your Google Drive.

### Key Point

**OAuth 2.0 → Authorization → Access Token**

OAuth 2.0 answers:

> "What can this application access?"

---

# OpenID Connect (OIDC)

## 12. OIDC

OIDC is an **authentication layer built on top of OAuth 2.0**.

It allows an application to verify the identity of the user.

Example:

**Sign in with Google**

    User
     ↓
    Google Login
     ↓
    Authentication
     ↓
    ID Token
     ↓
    Application knows who the user is

### Key Point

**OIDC → Authentication → ID Token**

OIDC can also involve:

- Access Token
- Refresh Token

---

## 13. OAuth 2.0 vs OIDC

| OAuth 2.0 | OIDC |
|---|---|
| Authorization | Authentication |
| "What can this app access?" | "Who is this user?" |
| Access Token | ID Token |
| Refresh Token may be used | Access + ID + Refresh Tokens may be involved |
| Grants access to protected resources | Provides identity information |

### Interview Answer

> OAuth 2.0 is used for authorization, while OIDC is an authentication layer built on top of OAuth 2.0. OAuth provides access tokens for accessing protected resources, while OIDC provides an ID token containing information about the authenticated user.

# API Key Authentication

## 15. API Keys

An API key is a secret credential used to identify and authenticate an API client.

Example:

    GET /api/data
    X-API-Key: abc123

Commonly used for:

- Server-to-server communication
- Public APIs
- Internal services
- Service integrations

API keys are generally **not a replacement for user authentication**.

---

# Basic Authentication

## 16. Basic Authentication

Credentials are sent using the `Authorization` header.

    Authorization: Basic base64(username:password)

Important:

Always use HTTPS because Base64 is **encoding, not encryption**.

---

# SAML

## 17. SAML

SAML is commonly used for enterprise **Single Sign-On (SSO)**.

Example:

    Employee
       ↓
    Company Login
       ↓
    Identity Provider
       ↓
    SAML Assertion
       ↓
    Application

Common in:

- Enterprise applications
- Corporate SSO
- Large organizations
- Identity providers such as Okta and Microsoft Entra ID

---

# MFA / 2FA

## 18. Multi-Factor Authentication

MFA requires multiple authentication factors.

Example:

    Password
       +
      OTP
       ↓
    Authenticated

Factors can include:

- **Something you know** → Password
- **Something you have** → Phone / Security Key
- **Something you are** → Fingerprint / Face

### 2FA vs MFA

- **2FA** → Exactly two authentication factors.
- **MFA** → Two or more authentication factors.

# Authorization

## 19. RBAC

**Role-Based Access Control**

Permissions are assigned to roles.

    Admin
     ├── Create User
     ├── Update User
     └── Delete User

    User
     └── View Profile

    User → Role → Permissions

Example:

    Vishal
      ↓
    Admin Role
      ↓
    Create / Update / Delete Users

---

## 20. ABAC

**Attribute-Based Access Control**

Access is based on attributes.

Example:

    User.department = "Engineering"
                AND
    Resource.department = "Engineering"
                ↓
              ALLOW

Attributes can include:

- User
- Role
- Department
- Location
- Resource
- Time

---

## 21. ACL

**Access Control List**

Permissions are attached directly to a resource.

Example:

    Document A

    Vishal → Read + Write
    Rahul  → Read
    Amit   → No Access

The resource maintains a list of users and their permissions.

---

## 22. ReBAC

**Relationship-Based Access Control**

Access depends on the relationship between the user and resource.

Example:

    User
      ↓
    Owner
      ↓
    Document

Owner can edit the document.

Another example:

    User
      ↓
    Member
      ↓
    Team
      ↓
    Team Resources

Team members can access team resources.

---

## 23. PBAC

**Policy-Based Access Control**

Access decisions are based on policies.

Example:

    IF
    user.role = "manager"
    AND
    resource.department = user.department
    THEN
    allow

Policies can combine:

- User attributes
- Resource attributes
- Roles
- Relationships
- Environment conditions

# Authentication vs Authorization Models

    Authentication
    │
    ├── Password
    ├── Session
    ├── JWT
    ├── OAuth 2.0
    ├── OIDC
    ├── API Key
    ├── Basic Auth
    ├── SAML
    ├── MFA
    └── Passkeys

    Authorization
    │
    ├── RBAC
    ├── ABAC
    ├── ACL
    ├── ReBAC
    └── PBAC

> **Note:** These categories are conceptual rather than mutually exclusive. For example, OAuth 2.0 is primarily an authorization framework, while OIDC adds authentication. JWT is a token format and can be used in different authentication/authorization architectures.

# Important Security Concepts

## 24. HTTPS

Always use HTTPS for authentication and authorization traffic.

HTTPS protects credentials, cookies, and tokens while they are transmitted over the network.

    Client
      │
      │ HTTPS
      ↓
    Server

Without HTTPS, an attacker on the network may be able to intercept sensitive data.

---

## 25. CSRF

**Cross-Site Request Forgery**

An attacker tricks a user's browser into making an unwanted authenticated request.

Example:

    Victim is logged in
           ↓
    Attacker creates malicious request
           ↓
    Victim's browser sends authentication cookie
           ↓
    Server accepts the request

Common protections:

- CSRF tokens
- SameSite cookies
- Checking Origin / Referer where appropriate

CSRF is particularly important when authentication credentials are automatically sent by the browser, such as cookies.

---

## 26. XSS

**Cross-Site Scripting**

An attacker injects malicious JavaScript into a web application.

Example:

    Attacker
       ↓
    Injects malicious JavaScript
       ↓
    Application renders it
       ↓
    Victim's browser executes it

Potential impact includes:

- Stealing data accessible to JavaScript
- Performing actions as the user
- Modifying page content
- Session compromise depending on the authentication design

Protection:

- Output encoding
- Input validation
- Content Security Policy (CSP)
- Avoid unsafe HTML rendering
- HTTP-only cookies for sensitive cookies

### Important

`HttpOnly` prevents JavaScript from directly reading a cookie, but it does **not** make an application immune to XSS. An XSS attack can still perform authenticated actions through the victim's browser.

# Quick Interview Summary

## Authentication

> Authentication verifies **who the user is**.

Examples:

- Password
- Session
- JWT
- OIDC
- MFA
- Passkeys

## Authorization

> Authorization determines **what an authenticated user is allowed to do**.

Examples:

- RBAC
- ABAC
- ACL
- ReBAC
- PBAC

## OAuth 2.0

> OAuth 2.0 is primarily an **authorization framework** used to obtain access tokens for protected resources.

## OIDC

> OIDC is an **authentication layer on top of OAuth 2.0** that allows an application to verify the user's identity using an ID token.

## Session

> Session-based authentication stores the authentication state on the server and typically sends a session identifier to the browser using a cookie.

## JWT

> JWT is a signed token format commonly used for stateless authentication and authorization. Its payload is readable unless additional encryption is used.

## Access Token

> An access token is used to access protected APIs and is generally short-lived.

## Refresh Token

> A refresh token is used to obtain a new access token after the current access token expires and should be protected more carefully.

## RBAC

> RBAC assigns permissions to roles, and users receive permissions through those roles.

## ABAC

> ABAC makes authorization decisions using attributes of the user, resource, action, and environment.

## ReBAC

> ReBAC makes authorization decisions based on relationships between users and resources.

## CSRF

> CSRF tricks an authenticated user's browser into sending an unwanted request. SameSite cookies and CSRF tokens are common defenses.

## XSS

> XSS occurs when an attacker injects malicious JavaScript that executes in another user's browser. Output encoding, CSP, and safe rendering practices help prevent it.
